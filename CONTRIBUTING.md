# Contributing to the Documentation

## Rules

1. Keep requirements specific and testable.
2. Mark every unresolved item as an assumption or open question.
3. Cite or link official sources for legal, scheme and utility statements.
4. Do not publish private credentials, customer data or personal documents.
5. Do not invent product models, prices, reviews, installation statistics or certifications.
6. Update the decision log when a decision changes scope or behaviour.
7. Keep the roadmap aligned with approved scope.

## Suggested change process

1. Open an issue describing the change.
2. Identify affected documents.
3. Update requirements and acceptance criteria.
4. Update decision log if needed.
5. Request business / technical review.
6. Merge after approval.

## Documentation style

Use clear headings, concise language, tables for structured requirements and checklists for validation. Prefer `snake_case` for proposed database field names.
